## Methodology

- A temporary, uncommitted admin script used `SUPABASE_SECRET_KEY` (service-role) only to call `auth.admin.createUser` for exactly one QA Auth user. No other direct-table writes were made with this script. The `on_auth_user_created` trigger auto-created the default `profiles` row (`role=STUDENT`, `academic_status=STUDYING`, legacy `student_status=ACTIVE`) — this default already satisfied the required student/profile state without any further direct mutation.
- `seedDemoUsers` was **not** invoked. The existing `DEMO_STAFF_EMAIL`/`DEMO_STAFF_PASSWORD` account (already present in Cloud from prior batches) was reused only to obtain a staff JWT — no new demo data was created.
- The QA user's password was generated randomly in-memory, never printed, and never committed. The credential file (local scratch, outside the repo) was deleted immediately after the run completed.
- Every business entity (program, cohort, profile assignment, research area, advisor, thesis, and its lifecycle transitions) was created/mutated exclusively through the real deployed REST routes, running the local Express API (`apps/api`) against the Cloud database — no direct SQL writes to business tables.
- After each create step, row counts filtered by the `QATMP-B5-FIX-` prefix were checked via read-only GET calls before proceeding to the next step, to rule out duplicates.
- No migrations (0039–0049) were run, no `db push`, no `psql` writes, no seed scripts. No existing data was modified or deleted. Nothing was committed, pushed, or deployed.

## Deviation from spec

- **`required_min = 1`, not `0`.** The deployed `programs.required_credits_min` column has `CHECK (required_credits_min > 0)` (migration 0015, already live in Cloud), so `0` is rejected by Postgres itself — not achievable via any real API call. This was flagged to a human reviewer before proceeding; the reviewer approved using the minimum valid value (`1`) instead, keeping `elective_credits_min = 0` and `thesis_credits_min = 0` exactly as specified (both columns allow `>= 0`).
- **Follow-up (this run, same date): the `required_credits_min=1` deviation was closed out.** The original run above deliberately made no enrollment/grade calls, so `required_credits_earned` stood at `0` — below the program's own `required_credits_min=1` — meaning the fixture's own eligibility condition was not yet actually satisfied (the report's earlier verdict was premature on this point). This follow-up used real Batch 1–3 REST/RPC endpoints to close the gap: one existing course was mapped onto the QA program as `REQUIRED`, one QA course class (prefix `QATMP-B5-FIX-CLASS-`) was opened in the already-live registration period, the QA student registered into it (reaching `CONFIRMED`), and staff entered + published a `PASS` grade for it. `required_credits_earned` is now `3` (the course's credit value), which is `>= required_credits_min (1)`. No new course/program/cohort/student was created; the existing QA program/student from the original run were reused as-is.
